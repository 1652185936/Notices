# 11 · 书写手感与画布资源 / 性能分析

> 对应用户诉求「手感和画布资源你来分析怎么弄」。本文是**方向与优先级**，不是泛泛而谈：每条都给「现状 → 问题 → 怎么改 → 鸿蒙4(无 GMS) 可行性」。落地由对应子任务执行。

---

## A. 书写手感（写起来「跟手、像真笔」）

手感 = **延迟** ×（**轨迹平滑** + **笔形真实** + **压感/倾斜响应**）。当前已做对了平滑与笔形，最大短板是**延迟**与**倾斜**。

### A1. 输入→显示延迟（最关键，目前最大短板）
- **现状**：书写帧 = 画基底位图 + 当前一笔走 Compose `Canvas`/`drawPath`。整条在制笔迹每帧用 `InkGeometry.strokeOutline` 重算轮廓并填充，走的是常规 Compose 重组+RenderThread 合成链路，端到端延迟通常 ~2–4 帧。
- **问题**：高端笔记 App（华为/享做/一笔记）跟手感来自**低延迟前缓冲渲染**（笔尖几乎贴着笔走），常规 Compose 链路追不上。
- **怎么改**（按性价比）：
  1. **运动预测（motion prediction）**——最低成本、收益明显。用最近 2–3 个点的速度外推 1 个「预测点」接在当前笔尖，补偿渲染延迟。抬笔时丢弃预测点。纯 Kotlin，零依赖，先做这个。
  2. **前缓冲低延迟渲染**——`androidx.graphics:graphics-core` 的 `GLFrontBufferedRenderer` / `CanvasFrontBufferedRenderer`，把「当前在制笔迹」画到前缓冲，绕过合成延迟。**Jetpack 库、不依赖 GMS**，鸿蒙4 安卓兼容层可用（需实测 GL 支持）。这是质变项，但工作量大，作为第二阶段。
  3. 在制笔迹**不要每帧全量重算轮廓**：只对「新增的那一小段」增量追加三角带/轮廓，已稳定段缓存。
- **鸿蒙4 可行性**：方案1 纯算法必可行；方案2 依赖 GL 前缓冲，需在雷电/真机实测 `GLFrontBufferedRenderer` 能否初始化，不行则退回方案1+3。

### A2. 倾斜 / 侧锋（目前完全没做，铅笔/秀丽笔的灵魂）
- **现状**：只用了 `change.pressure`，没用倾斜。
- **怎么改**：从原始 `MotionEvent` 读 `AXIS_TILT` 与 `AXIS_ORIENTATION`（Compose 下需经 `PointerInputChange` 的原生事件或自定义 `pointerInteropFilter` 拿 MotionEvent）。
  - **铅笔**：倾斜越大 → 笔宽变宽、芯层变淡、毛边层变宽（侧锋涂抹质感）。
  - **秀丽笔/钢笔**：用 orientation 决定笔锋朝向，做「书法侧锋」非对称变宽。
- **鸿蒙4 可行性**：取决于侧载手写笔是否上报 tilt 轴。M-Pencil 类一般支持；先探测 `device.getMotionRange(AXIS_TILT)`，没有就静默降级到纯压感（不报错）。

### A3. 压感曲线与每支笔参数（华为：每支笔有独立灵敏度）
- **现状**：`widthFactor` 里压感映射写死 `0.45 + p*1.05`；速度映射各笔固定常数。
- **怎么改**：把压感→笔宽做成**可调曲线**（gamma），并按 CLAUDE.md §4 队列「每支笔独立参数面板」暴露：铅笔=压感灵敏度，秀丽笔=稳定度（防抖强度）。先把曲线参数化、留接口，UI 面板后续接。

### A4. 防抖 / 稳定度（秀丽笔写慢字会抖）
- 现状只有笔宽指数平滑，**没有轨迹防抖**。加一个可选的「位置低通/拉绳（pulled-string）稳定器」：笔尖跟随一个带阻尼的目标点，慢速书写更稳。秀丽笔默认强、钢笔默认弱。

## B. 画布资源 / 性能（多笔、大图、长时间书写不卡不爆内存）

### B1. 平移/缩放期的全量矢量兜底（首要性能风险）
- **现状**：基底烘焙位图（`BakeStamp` + 60ms 防抖重烘）很好；但**平移/缩放过程中**位图失配，每帧回退到 `drawCommittedWorld` 全量重画所有元素。笔迹一多（几百条），拖动就掉帧。
- **怎么改**：
  - 平移/缩放期**直接位移/缩放上一张烘焙位图**（`drawImage` 带平移缩放变换）做即时近似，停手再重烘清晰版——而不是全量重画矢量。代价是拖动时轻微模糊，松手即清晰，华为也是这套。
  - 进一步：**世界分块（tile）缓存**，只重画进入视口的脏块。工作量大，元素到上千条再上。

### B2. 图片内存（大图直接 OOM 风险）
- **现状**：`insertImage` 显示尺寸限到 900px 宽，但 `BitmapFactory.decodeFile` **解码的是全分辨率原图**进内存；多张高清照片 → 内存暴涨。
- **怎么改**：解码时用 `inJustDecodeBounds` 拿原尺寸后设 `inSampleSize` 按目标显示尺寸**降采样解码**；导入时可另存一份压缩缩略图。导出再按需读原图。

### B3. 撤销栈深拷贝（大文档内存）
- **现状**：`undoStack` 每步存整份 `elements.toList()`（最多 80 份）。大画布下内存与拷贝开销大。
- **怎么改**：渐进改为**命令式撤销**（记录 add/remove/transform 的最小 diff）。非紧急，元素多了再上；先把上限从 80 调到合理值并只在真正变更时压栈。

### B4. Path/轮廓缓存
- **现状**：`inkCache` 按 `id+点数+首末点` 缓存轮廓 Path，800 条清空——合理。注意套索平移会改首末点使 key 失效自动重建，符合预期。保持。

### B5. 持久化
- **现状**：每次 `markDirty` 防抖 1s 后整份 `CanvasContent` 序列化落库。大文档下整序列化偏重。
- **怎么改**：可接受现状；后续若卡，改为脏标记 + 增量或后台线程序列化（已在 `Dispatchers` 外，注意别在主线程序列化大 JSON）。

## C. 优先级建议（先做收益最高、风险最低的）
1. **运动预测**（A1.1）——纯算法，立刻提升跟手感。
2. **平移缩放期位图兜底**（B1）——纯算法，消除拖动掉帧。
3. **图片降采样解码**（B2）——防 OOM，必做。
4. **倾斜/侧锋**（A2）——质感质变，但依赖硬件，先探测后降级。
5. **前缓冲低延迟渲染**（A1.2）——质变但工作量大，二阶段，需真机实测 GL。
6. 每支笔独立参数面板 + 压感曲线（A3）、稳定度（A4）——配合「笔刷设置浮层」扩展。

> 全部方案均**不依赖 GMS**：运动预测/兜底/降采样/撤销均为纯 Android；低延迟用 Jetpack `graphics-core`；倾斜走原生 `MotionEvent` 轴。鸿蒙4 唯二需真机/模拟器实测的是：`GLFrontBufferedRenderer` 可用性、手写笔是否上报 tilt 轴。
